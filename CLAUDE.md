# TDPyMovieplayer — Project Instructions

## TouchDesigner Conventions

The general code rules — verify API symbols against the install, no silent `getattr` fallbacks, shared `tdpy` files changed upstream, bytecode cleared during control runs, inert controls named in a handover — are in the vault's `.claude/rules/300-code.md`. This file holds what is specific to TouchDesigner and this project.

- **The install describes itself in five places:** the offline wiki under `Samples/Learn/OfflineHelp`, `Config/TDParameterHelp.json`, the type stubs under `bin/Lib/tdi/ops`, the stock callback files under `bin/Lib/tdutils/DATScripts`, and the strings in `bin/libTD.dll`. A live `python` query in the app settles anything they don't. Enums are **not** on the `td` module — `ParMode`, `JustifyType` and friends live in `tdutils.TDDefinitions`.

- **A callback's name and signature come from `bin/Lib/tdutils/DATScripts/`.** One file per operator that has callbacks (`timerCHOP_callbacks.py`, `chopexecuteDAT.py`, `listCOMP_callbacks.py`), carrying the exact argument list and a docstring per argument. The wiki's prose is not enough: it names the Timer CHOP's cycle callback in passing and leaves the reader to guess which end of a cycle it means. `timerCHOP_callbacks.py` has **both** — `onCycleStart(timerOp, segment, cycle)` at line 120, *"Called when a cycle starts"*, and `onCycle(timerOp, segment, cycle)` at line 147, *"Called when a cycle completes"*. The dwell uses `onCycleStart`, which is why `player.on_dwell` has to refuse cycle 0: the timer starting is a cycle beginning. `onDone(timerOp, segment, interrupt)` is the one the fade timer uses, since a fade runs once rather than cycling.

- **A channel name that is not in `libTD.dll` is not a channel name — but being in it does not make it *this operator's*.** An operator's output channels are reachable only through an Info CHOP, and their names are documented unevenly: the Timer CHOP's help names `segment_pulse` outright and leaves its cycle-pulse channel unnamed. Grepping the binary settles absence — `loop_frame` and `segment_pulse` are in there and `cycle_pulse` is not, which is why the dwell timer is read through its callback rather than watched as a channel.

    **The binary cannot settle presence.** `dropped_frames` is in `libTD.dll` and is the Video Device Out TOP's; the Movie File In TOP has no such channel. The grep would have passed it and the readout would have been blank. For presence, the **OfflineHelp page's "Info CHOP Channels" section is the authority** — and where an operator's own page gives them only in prose, as the Movie File In TOP's does, a sibling operator sharing the channel set has the enumerated list: the file-reading TOPs' set is written out in full on `Point_File_In_TOP.htm`, identifiable as the right one because `loop_frame` is in it. Use the binary to refuse a name and the help to accept one.
- **A menu item's internal name is worth reading off the live parameter, whatever the help says.** `set_menu` resolves against it and reports what it landed on, which is the only reason Asset Paths on the Engine COMP is `toe`: `Engine_COMP.htm`'s own parameter table calls that item `project`. The help's parameter table is a source for *which* parameters exist, not for what a menu's items are called — a wrong item leaves the default in place and says nothing, so `set_menu` refusing one is the mechanism that has to catch it.

- **An Engine COMP is a one-way boundary with outputs coming back.** Custom parameters on the `.tox`'s top level cross host to engine only — the help is explicit that nothing inside may set one — so a command goes out as a pulse parameter and everything the host learns comes back as a TOP, CHOP or DAT output. Settings therefore reach the engine as an **expression** on the Engine COMP rather than a binding, since a binding is two-way and would claim something the boundary cannot do. Relative paths inside the component resolve against the `.tox` until Asset Paths says otherwise, which is what makes the clip paths work.

- **Where two of the install's five descriptions disagree, prefer the operator that has only one spelling.** The Math CHOP's Common-page rename parameters are `commonrenamefrom`/`commonrenameto` on `Math_CHOP.htm` and `renamefrom`/`renameto` in the type stub at `bin/Lib/tdi/ops/chops/mathCHOP.py`. Nothing on disk settles which the live parameter answers to, and `set_par` reporting a miss would only say that one of them was wrong. The Rename CHOP's own parameters are `renamefrom`/`renameto` in **both**, so the mixer uses dedicated Rename CHOPs and the question never gets asked. Two extra nodes is a cheap price for a name that is not a coin flip — and cheaper than the alternative, which is a build that half-works on one machine.

- **Display indices are 0-based.** A Window COMP's `Display` parameter indexes the Monitors DAT from 0, and TouchDesigner silently opens the window somewhere else rather than refusing an out-of-range value. Derive a bounds check from the Monitors DAT row count, not from the same assumption as the value being checked.
- **Panel widgets must live inside a panel-type COMP** (a containerCOMP), not a baseCOMP. Put one in a baseCOMP and it simply doesn't render — no error.
- **Add new controls to the existing `controlPanelWindow`**, rather than creating a new panel or window.
- **The Perform Window is a project setting, not a window's property.** It lives in the Window Placement dialog, so a project with two Window COMPs and no opinion gets whichever one that dialog already named. `setperform` is the pulse that claims it, and the build pulses it on `videoPlayerWindow` every run — the same reasoning as clear-and-rebuild, since nothing else keeps the claim true. `performance` opens a window in Perform Mode *without* changing the default, and `winopen` is a floating window its own help says "should not be used for putting final rendered content to outputs".
- **MIDI needs a device mapping, and the mapping is an authorable table.** A MIDI In DAT or CHOP left on its defaults receives nothing, which is why `_ensure_device_table` exists. The documented way to make a mapping is the MIDI Device Mapper dialog, which writes into `/local`, inside the `.toe`. But what it writes is an ordinary five-column Table DAT at `/local/midi/device` (`id`, `indevice`, `outdevice`, `definition`, `channel`), so the build authors it and the dialog becomes a **one-time discovery step** rather than setup. Converge rather than clear: keep a `definition` set by hand, and leave rows for other device ids alone. A controller's CC numbers are **learned from the running device**, never taken from the manufacturer's chart — templates change them — and note that *channel* names three different things here: the MIDI channel the messages carry, the device table's `channel` column, and the hardware's channel-strip label.

- **Nothing may require the `.toe` to have been saved.** It carries one Execute DAT and no project state, and every setting the project depends on is written by `build.py` on launch. A setting made by hand in the GUI is a note to add it to the build, not a reason to save.
- **`COMP.create()` appends a digit to the name**, even when the name is free. Use `startup.create()` anywhere the new node's name is referred to again.

## Running the tests

`dev_vEnv/Scripts/python -m pytest`. The other environment, `TDPyMovieplayer_vEnv`, is TouchDesigner's and has no pytest - and `python` on this machine's PATH resolves to it, so a bare `python -m pytest` fails and reads as a suite that cannot run. `requirements-dev.txt` says how to rebuild `dev_vEnv`.

**Rebuild does not reload `spikes/`.** `startup.reload()` drops modules under `tdpy.` only, so after editing a spike, reload it by hand before running it: `import importlib, spikes.baseline; b = importlib.reload(spikes.baseline)`.

## Running a control

Clear the bytecode cache in this repository, leaving the virtual environment alone: `find . -name __pycache__ -type d -not -path "./*_vEnv/*" -exec rm -rf {} +`.
